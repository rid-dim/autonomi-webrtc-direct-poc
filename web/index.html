Autonomi over WebRTC-Direct

An ordinary web page, pulling a file straight off the Autonomi network. No browser extension. No local daemon or relay. Nothing installed, and no process running on this machine. Just a page and a WebRTC connection.

What is being demonstrated

Browsers speak QUIC perfectly well — HTTP/3 rides on it. What they cannot do is open a raw connection to an arbitrary host and speak an arbitrary protocol: there is no socket API, only HTTP/3 and WebTransport. Autonomi nodes run their own QUIC-based protocol with their own handshake and identity model, and they have neither a DNS name nor a CA-issued certificate. That combination — not QUIC itself — is what puts them out of a browser's reach.

So the endpoint this page talks to is a stand-in for a node that also listens for browsers — it answers exactly one question, “what bytes are stored at this address?”, and does nothing else. It is not a gateway: it never sees plaintext and cannot alter a byte.

So the question this answers is: if Autonomi nodes offered a WebRTC-Direct listener alongside QUIC, could any website embed network content directly? The answer below is yes — and were nodes to do that, this middle box would simply disappear. Nothing in the browser would change.

Where this could go

A WebRTC-Direct listener only works on a node that is publicly reachable, which at first glance limits how much of the network browsers can draw on. But a public node does not have to serve the data — it could just broker: accept the browser, help it establish a connection to another node, and step out of the path.

Crucially, that second node does not need to hold the chunk either. It would do exactly what the endpoint in this demo does today — an ordinary DHT lookup over Kademlia XOR routing, then hand the bytes back. Any node can answer any address, so serving browsers is not tied to who stores what. Browser load spreads across the whole network instead of concentrating on the publicly-reachable minority, and a broker's own cost stays near zero regardless of file size.

libp2p already has the machinery for this shape — browser-to-private-peer WebRTC, with the connection negotiated over a relayed hop. The open questions are which NATs it traverses without a fallback relay, and how that squares with Autonomi's own QUIC-based hole punching, which is a different mechanism from the one browsers use.

WebRTC-Direct is not the only candidate. WebTransport reaches a host the same way — the browser pins a hash of the server's self-signed certificate instead of validating a chain — and it became available in every current browser in March 2026. It is the better-behaved option in several respects: real QUIC congestion control, no SRTP or SDP machinery, and none of the deprecation risk hanging over the SDP munging that WebRTC-Direct depends on. The catch is operational: a pinned WebTransport certificate may be valid for at most two weeks, so the hash a page has baked in expires and must be re-published continuously. WebRTC's certificate hash is stable for as long as the node keeps its key, which is what makes the address on this page something you can simply write down. Worth evaluating properly rather than assuming either way.

A browser listener need not cost a second port. The obvious operational objection — another open UDP port for every operator to configure — is avoidable: QUIC and WebRTC can share one, and the demultiplexing scheme is standardised in RFC 9443. Route on the first byte of each datagram: STUN and DTLS to the WebRTC stack, everything from 64 up to the existing QUIC stack. One firewall rule, existing ip:port bootstrap lists still valid, the same address serving both. The catch is that such a node must not send grease_quic_bit, since the scheme depends on QUIC's fixed bit being set.

That also settles a question we had been treating as speculative: whether nodes should speak this channel to each other to reduce open ports. They get the port saving anyway, so the remaining case for it is weak — SCTP over DTLS carries less well than QUIC, the handshake costs several more round trips, and the DTLS stacks here lag on crypto agility. This PoC hit exactly that: current Chrome offers post-quantum key agreement which the Rust DTLS implementation cannot perform at all, sitting awkwardly beside Autonomi's pure-PQC direction. As a browser-facing edge, WebRTC earns its place; as a replacement for node-to-node QUIC, it does not.

What this removes

  • No browser extension. Plain page JavaScript and WASM.
  • No local daemon, relay or gateway. Nothing listening on localhost.
  • No install, no process rights. Nothing to run on the visitor's machine.
  • No DNS name and no CA certificate for the node — a bare IP is enough, because the browser pins the certificate's hash instead of validating a chain.
  • No trusted intermediary. Point the page at anyone's endpoint and the integrity and confidentiality guarantees are identical.

Which means any website could embed Autonomi content the way it embeds an image today.
